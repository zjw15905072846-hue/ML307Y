# MQTT 顺序与订阅编号修复

本次按用户批准的流程修改，版本标记为 mqtt-flow-20260928。

```text
设备开机
   │
   ▼
4G 入网 / PDP 激活，加载本机身份和平台配置
   │
   ▼
SDK 建立 TCP（配置 TLS 时完成握手），发送 CONNECT
   │
   ▼
CONNACK 成功
   │
   ▼
发送下行 SUBSCRIBE，保存本次消息编号
   │
   ├─ 请求失败、拒绝或等待超时 → 断开后延时重连并重新订阅
   ▼
匹配 SUBACK 且授权成功
   │
   ▼
发送注册包并打印实际报文
   │
   ├─ 业务回复失败或超时 → 保持未注册，按间隔重试
   ▼
匹配平台注册成功回复
   │
   ├─ 按键 → 持久保存并执行声光 → 发送报警 → 等匹配业务回复
   │                                      ├─ 失败或超时 → 保留并重试
   │                                      └─ FF/00 成功 → 删除对应记录
   ├─ 业务心跳 → 每 12 小时发送；保留原有注册后的启动心跳
   └─ MQTT 保活 → SDK 按独立 keepalive 配置执行
   │
   ▼
持续在线，不因报警队列为空主动断开
   │
   └─ 网络断开 → 重连、订阅、注册，再重试未确认报警
```

## 缺陷与修复

底包 cm_mqtt_client_subscribe 使用当前消息编号编码请求，随后调用 cm_mqtt_client_msg_id_add；cm_mqtt_client_publish 具有相同编号推进语义。get_msgid 只返回当前计数值。旧代码发送后读取，保存的是下一编号，因此正确的 SUBACK/PUBACK 无法匹配。

修复为在发送前获取并验证编号，然后保存并提交请求。所有请求由后台串行调用；不通过忽略编号或跳过 SUBACK 放宽确认。订阅增加请求编号、调用结果、收到的 SUBACK 编号和结果打印，超时也单独打印。原有空指针释放修复保留。

另取消业务空闲时主动断开，保持后台轮询。现有平台注册门控、业务回执匹配、报警持久重试和实际报文打印保留；MQTT PUBACK 不能删除报警。

## 验证与实板检查

编号复现测试先在旧代码上失败于订阅在线断言，修复后通过；持续在线测试先在旧代码上检测到主动 stop，修复后通过。完整测试和构建结果见项目内 out/mqtt-flow-20260928 保存的日志及 verification.json。

上板确认新版本标记后，观察 mqtt-subscribe-id 与 mqtt-suback-id 是否相同、mqtt-suback-result 是否为 0，以及随后实际 registration 报文和 registration-confirmed。再按键检查报警发送、声光和匹配业务回复，断网恢复后检查未确认报警重试。平台不回业务确认时仍必须保留记录；构建和模拟测试不能证明平台业务成功。
