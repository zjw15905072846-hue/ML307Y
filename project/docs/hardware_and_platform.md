# 硬件和平台核验边界

依据本轮确认的原理图和产品规格保留接线，不用旧 SDK 的 GPIO 数字替代 CM 编号。下面的绑定状态来自当前 SDK 头文件、示例、静态库与配套 ELF 的只读检查，不是实机测试结论。

| 功能 | 原板依据 | 当前实现与启用条件 |
|---|---|---|
| 按键 | K1、K2 并联；WAKUP0 网络接模组物理 26 脚并在按下时接地；原理图将该脚标为 RSV | 当前底包 cm_dtr_init 使用 AGPIO_PIN0=100；底包扩展直接配置 HAL 输入上拉并轮询，不创建 DTR 休眠任务，不使用表外 CM GPIO26 |
| LED | ADC1 网经 R6=3.6kΩ 到 Q2=S8050 基极；物理 96 脚，高亮低灭 | 用户于 2026-09-27 要求启用；当前底包 CM_ADC_1→HAL_ADC4→GPIO_PIN_B=41，扩展 HAL 数字输出，初始化关闭；41 是 HAL 标识，不是 CM GPIO 编号 |
| 蜂鸣器 | PWM0 网经 Q3 到 BZ1；物理 74 脚 | 当前库对应 CM GPIO16，GPIO 必须用 FUNCTION3；PWM 使用 DEV_0、FUNCTION1；本轮保持原有 GPIO 方式，有源/无源类型和载波尚待实物确认 |
| 电池 | 模组 VBAT | cm_adc_vbat_read；校验合理电压范围；不伪造电量百分比 |
| 充电 | TP4054 CHRG 未接模组 | 不生成正在充电或充满事件 |
| 唤醒 | 原板接线及实际模组版本 | wake_verified=false；保持工作锁，不启用自动休眠或深睡 |

库中可核实的逻辑 GPIO 0～17 依次对应物理：
16、25、49、76、77、86、87、17、18、19、22、23、28、29、20、21、74、75。
头文件枚举范围较大，并不能证明表外编号有实际映射。

2026-09-27 核验发现：物理 26 脚的 IOMUX 功能掩码只有 0x02，旧 FUNCTION2 必然返回 -1；CM GPIO 映射表仅有 18 项，不能传入 26。物理 74 脚对应 CM GPIO16，驱动明确要求 FUNCTION3，旧 FUNCTION2 会返回 -3。新测试按真实约束拒绝这些错误参数。

底包扩展的 HAL 结构按随附 ELF 的 DWARF 核对：总长 40 字节，中断回调偏移 24，keep 偏移 32；构建加入静态断言，并把源码、头文件纳入底包身份。按键使用输入模式 33/上拉 1；LED 使用输出模式 36/下拉 2，先预置低电平，再初始化和回读输出。LED 不调用 ADC 采样。UART0 的物理 17/18 脚初始化成功只证明串口；前台仍保持工作锁并轮询，未启用睡眠唤醒。

用户提供的 AT 硬件手册第 20/24/47 页仍把 26 脚标为 RSV，第 37 页只描述 96 脚 ADC 输入（0～1.4V）。因此上述 OpenCPU 私有 HAL 路径是依据当前底包实现及用户明确指定接线的实板验证方案，不能当作 AT 手册对这些用法的保证。必须实测松开为高、按下为低、一次稳定按下新增一条报警，以及 96 脚高亮低灭。HAL 回读和测试通过都不代表板端电气行为已验证。

## 平台联调尚缺的输入

- 铠湾 Broker、端口、账户、32 字节厂商码、厂商 ID、AES 密钥。
- AES 明文模式、CRC 字节序、注册/心跳/报警实际样例；手报 0x04、紧急报警 0x0C 对应平台业务验证。
- 未知电量、CSQ、时间的编码约定。默认没有有效百分比或未知值约定时拒绝构造报文。
- UTC 时间来源及其时区验证。默认不把模组 RTC 候选值当作已确认 UTC。
- 恢复历史事件的补报与去重规则。AB_REPLAY_MODE=0 默认保留恢复记录并报告待配置；1 需要真实发生 UTC，2 仅可在平台确认允许实时重投后启用。
- 如启用 TLS，需匹配的 CA 文件和通道配置；当前适配使用验证证书及 SNI，没有关闭验证来绕过问题。

16 位协议序号目前保留旧实现的防串单策略：跨重启持久递增，不擅自回卷；耗尽后明确报错并保留记录。长期投递的回卷/去重规则仍需平台确认，不能声称已支持无限次序号分配。

## 文件、加密及底包

项目底包只扩展 project_base_identity、文件原始探测、随机源与所需 AES 导出。文件探测仅将底层 LittleFS -2 映射为“不存在”，其他负值保持 I/O 错误。CM 层的 cm_fs_exist 会合并错误，因此不用于初始化判断。

CM 头文件注明 ML307Y 写模式可自动创建父目录。每个产品使用 products/<namespace>/alarm.a 与 alarm.b；写入、同步、关闭、回读和 CRC 验证完成才提交。一个完整槽加一个损坏槽可恢复完整代数，并记录告警；再复用坏槽前先保留为 .corrupt.N。外来产品或未知完整头格式、两个槽均损坏、读取错误都停止自动写入。

应用采用当前 3.6.4 头文件；底包 ELF 的 AES 上下文 size=288、rk_offset=8、buf=16，与应用编译期断言一致。主机参考 AES 版本为 3.2.1，其源码和头文件只在主机测试内成套使用。没有把旧 SDK 的库或结构体链接到新固件。

MQTT 客户端上下文在运行期间保持有效；SDK 回调立即复制数据，后台 poll 串行处理。连接代数、订阅/发布编号及业务序号共同过滤旧消息。主机模型覆盖排队的旧回调、拥塞和重连；真实 SDK 的线程调度、断开后回调次序及网络分段行为仍要实网验证。

## 上板验收建议

1. 先核验引脚和蜂鸣器类型；测量 30 ms 消抖后的响应与睡眠唤醒恢复延迟。
2. 用逻辑分析仪观察 1 秒常亮及六个 250/250 ms 闪鸣周期；弱网、文件慢写期间分别观察。
3. 平台在 0.5、2、4、10、34 秒附近回执；测试重按、旧回执、重复回执、拒绝和掉网重连。
4. 在文件写入、同步、回读及确认删除时分别切断电源；确认旧完整记录保留，错误不触发清空。
5. 测量 VBAT 发射压降、声光电流、持续重试电流和待机功耗。没有未确认事件且唤醒验证完成后，才测试普通休眠。

本轮没有烧录设备、连接真实铠湾账户或进行上述实机测量。
